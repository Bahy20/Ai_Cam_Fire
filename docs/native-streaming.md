# Native MiniCPM webcam streaming

The live path keeps one browser WSS connection to the CPU gateway and one authenticated WSS connection from the gateway to the dedicated Modal H100. Only exact, usable, quality-checked images reach the model. YOLO and Scout do not run in this deployment. Recorded uploads use a separate image-batch GPU pool and cannot mutate live KV state.

The active adapter is `analysis/visual_stream.py`. It uses MiniCPM-o 4.5 native `streaming_prefill` with an image and explicit current-image question, followed by text-only `streaming_generate`. Every processed image has its own strict JSON report and original source timestamp. It does not use the old forced-speech duplex adapter or repeatedly call an HTTP image endpoint. Audio and speech synthesis are disabled. The model is pinned in `analysis/minicpm_contract.py`.

The browser requests 30-fps preview and sends up to five JPEGs per second. The gateway samples at most three per second. The GPU processes one step at a time, with a one-second minimum interval and a single latest pending frame; actual visual inference takes several seconds. Older pending frames are replaced instead of queued. This is not 30-fps analysis. The exact adapter passed fifteen H100 control frames: warm GPU report time was1.768–2.012seconds (median1.908seconds), initial generation4.082seconds, with16.84GiB peak allocated GPU memory. These are GPU-step probe timings, not cold-start or public latency guarantees.

Context is reused across images but reset before 2,800 cached tokens. The pinned upstream text-only sliding-window trimmer produced repeated invalid output around 4,038 tokens; explicit bounded context epochs avoid that reproduced path. Its internal trim watermarks are set above the application bound. An over-limit or malformed report clears model context. This reset never clears validated incident history in the CPU coordinator. New sessions reset model context; source timestamps are never rebased.

Only one authenticated session owns the native model. Disconnect retains the model lock while a bounded inference drains, up to 15 seconds. An authenticated busy reconnect receives WS close 1013; the CPU proxy retries a bounded schedule totaling 15.75 seconds. Authentication failures are not retried. An upstream loss or invalid report immediately revokes monitoring evidence while retaining validated hazards. Pending frames and old sent-evidence mappings are cleared across reconnects.

Cold startup is explicit in the page, with elapsed time and guidance to keep the camera open. Dark/blank input, invalid model output and unavailable upstream service have distinct reasons. Neither listening nor connecting establishes a negative scene. Health reports `live_vlm_mode: native_visual_stream`; actual live results report `native_stream.engine: minicpm-native-visual`, processed step count, context epoch, cached tokens and frame timestamps.

The shared `minicpm-only-v3` coordinator requires three valid agreeing reports across at least two seconds, within an eight-second pool that expires at ten seconds, before clear-scene or reviewed-camera (`EXPECTED_LIGHTER_CAMERAS`) lighter monitoring. Smoke, material burning, separate flames, occlusion and conflicting findings prevent lighter downgrades. A hazard alert latches on two valid reports of smoke, burning material or a separate flame within 20 seconds; invalid or uncertain reports and reconnects between them do not discard the first, while three consecutive clear reports dismiss a pending single report. A single live smoke/material report shows `hazard_unconfirmed`; an upload that ends on an unconfirmed report is flagged for inspection. The visual session resets its model context after any hazard report, so the next image is judged fresh. Latched hazards survive loss of view, and while latched every newer hazard report refreshes the alert so a stale operator review is rejected. Because reports can arrive several seconds apart (cold GPU, reconnects), a latched alert's current priority is restored after eight consecutive valid clear reports, each at most 15 seconds apart, with the latest one current; gaps, invalid or non-clear reports, including rejected stale or unusable non-clear reports, reset the streak. Incident history stays visible and operator review resets the incident. Cause remains unverified. See `docs/model-only-analysis.md` for policy and public verification evidence.

Implementation: `analysis/visual_stream.py`, `analysis/native_server.py`, `analysis/src/native-stream.js`, `analysis/src/vlm-coordinator.js`, and `NativeLive` in `deploy/modal_app.py`. Both GPU pools have zero minimum containers and can run concurrently; actual inference consumes Modal credits. H100 was selected for live latency: on the public L40S replay, correct reports took2.8–3.5seconds plus transport lag, so three observations arrived too late for the unchanged10second oldest-evidence bound. Upload inference stays on L40S. Compact report experiments failed schema or recognition controls and were not deployed.

## Public deployment verification, 23 October 2026

The existing tester page is deployed with native streaming enabled. An authenticated tester-cookie WSS replay sent 429 recorded JPEG control frames through the public CPU gateway. The GPU completed 88 successive native steps in one connection; context grew from 332 tokens, reached 4,079 tokens and trimmed three times. Native compute duration was 131–731 ms, median 147 ms. The first GPU connection took about 62 seconds to produce its first native heartbeat, including cold startup. A second connection completed eight steps with a fresh counter and context starting at 332 tokens; no previous assessment was restored. Its first heartbeat took 9.31 seconds. Direct unauthenticated access to the native GPU WebSocket was rejected with HTTP 403.

This verifies native transport, persistent model state, bounded context and reconnect isolation. It does not establish recognition accuracy: the stream produced one complete lighter report, then mostly listened through later room/wood changes. The burning-wood controls did not receive fresh structured reports, and detector/policy priority remained urgent. The native mode is deployed for testing, with those limitations visible rather than treated as evidence of safety. The controls were prerecorded images, not a newly captured physical webcam test.

Local suites passed 64 JavaScript tests, 104 script Python tests and three detector tests. A read-only review verified the fix preventing delayed pre-gap or previous-incident native reports from qualifying a new lighter-monitoring lease. Public evidence: `deployed-health.json`, `deployed-wss-persistent.json`, `deployed-wss-reset.json`, `deployed-summary.json` and `auth.log` under `.hermes/native-streaming/`.

## Reporting and priority follow-up, 24 October 2026
