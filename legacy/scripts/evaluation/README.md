# Annotation and replay protocol

`handheld-priority-corpus.json` is the strict, versioned corpus for the lighter-priority work. It currently lists the three existing recordings as development-only by SHA-256. Their interval labels, onset bounds, visibility review, and reviewer are still null; null is unmeasured, not a negative. `handheld-corpus.mjs` rejects a recording identity or source hash split across development and held-out, requires a reviewer for measured labels, requires every lighter-to-material example to have a nonempty actionable interval and onset bounds, and rejects contradictory overlapping lighter-only/actionable intervals. Its coverage summary requires three reviewed recordings per category in both development and held-out, three fully labeled lighter-to-material transitions per split, and measured controlled-lighter exposure in both splits. The current corpus therefore blocks model selection and the release gate.

The readiness report has a separate `edge_handheld_model` gate. Pass its evidence in the JSON accepted by `scripts/evaluate_analysis.mjs --readiness-evidence FILE`. It must pin `model_bundle_sha256`, `weights_sha256`, and `quality_profile_sha256`; include `fire`, `smoke`, `lighter_flame`, and `secondary_burning` in `class_mapping`; and document cleared data rights, a frozen bundle, complete development coverage, a real candidate-path replay, measured CPU inference (`p95_inference_ms`), and a measured `uncertain_rate`. Both `development_unsafe_monitor_intervals` and `development_missed_actionable_transitions` must be measured zero. The held-out evidence must carry the same `model_bundle_sha256` as the qualified model stage, so a report for another model cannot satisfy the release gate. These fields are evidence claims: include immutable reports and source paths; a green unit test does not create real model evidence.

The ConFire paper describes image-level `no fire`, `controlled fire`, and `dangerous fire` categories, including lighter scenes under controlled fire. That may be useful for research experiments, but it does not provide the required labeled lighter-to-material video transitions; the linked Kaggle page did not expose licensing details in the available metadata view. Treat it as unapproved until the exact data and model rights are verified, and never use it as held-out evidence. See the [paper](https://www.nature.com/articles/s41598-026-48743-5) and [linked dataset page](https://www.kaggle.com/datasets/duongtm3012/confire).

`analysis-policy-labels.json` describes three development clips using the available user evidence. It does not supply forensic cause labels or independent held-out footage. `held-out-corpus.template.json` lists missing acquisitions for smoke, contained flame, burning material, reflections, and obscured scenes. Its `status: missing` entries cannot be replayed or scored as available evidence. No substitute synthetic video is part of this corpus.

Annotate complete source videos before inspecting model answers. Separate development and held-out clips by original video, session, and camera. Preserve who annotated the footage, their evidence basis, uncertainty, and source identity. Assign `visible_flame_present` and `actionable_fire_present` independently: a contained lighter may visibly burn while receiving an interval `monitor` policy only with reviewed `expected_handheld_flame_use` context plus fresh local candidate evidence and matching scene support. The default third-clip policy expects urgent review without that configured context. For a reviewed-context run, make an explicit annotation copy setting `interval_priority_expected: monitor` and `scene_expected: contained_tool_flame`; retain an independent live-priority expectation because a historical monitor assessment cannot clear live urgency. Do not infer any expectation from the model's output. `--camera-prefix NAME` supplies deterministic camera names NAME-0, NAME-1, NAME-2 for stationary-source context configuration. A label of null means unmeasured. `fire_present` remains a compatibility alias for visible flame. Neither priority nor scene classification proves physical safety, ignition cause, fuel, fire class, or hazard absence.

Use `split: development|held_out` and `category: smoke|contained|material|reflection|obscured`. Fill `duration_ms`, `visible_flame_onset_ms` and `actionable_onset_ms` only when independently measured in the source video. Legacy `onset_ms` remains the flame onset alias. Do not use the system's confirmation timestamp or model response to manufacture onset ground truth.

When replaying against a deployed Worker, use new camera IDs for each run. A
camera's V2 upload generation persists in its Durable Object, so reusing a
camera prefix with a new local session state gets `camera_generation_conflict`
(HTTP 409) and uploads no frames. Configure reviewed camera context for the
new ID before deployment; the isolated three-video script does both steps.

Example replay, against a running local evaluation Worker:

```powershell
node scripts/test_edge_runtime.mjs --worker http://127.0.0.1:8791 --out NEW_DIRECTORY --video PATH_TO_VIDEO --annotations scripts/evaluation/analysis-policy-labels.json --require-ai --realtime
node scripts/evaluate_analysis.mjs --run-dir NEW_DIRECTORY --annotations scripts/evaluation/analysis-policy-labels.json --output NEW_REPORT.json
```

The evaluator requires exactly one captured run for each annotation. For a subset replay, create a separate annotation file containing exactly that subset; do not silently remove clips from the requested denominator. A complete negative replay requires explicit `confirmation:null`, no investigation or AI job, complete frame upload and idle analysis. `--require-ai` applies to confirmed positive investigations; correct negatives need no AI call.

`detection_counts`, `flame_detection_counts` and the legacy false-alert rate retain visible-flame semantics. `actionable_incident_counts` compares the latest live source priority to actionable labels; `inspect_urgently` and `escalate` count as actionable. An assessment scoped `observed_interval` is historical and never changes this live metric. `false_urgent_alerts_per_camera_hour` counts distinct incidents ever announced live urgent, including those later downgraded, over all labeled actionable-negative camera exposure. Historical interval-only updates do not count as live alerts. It requires complete urgent-event capture and independently measured negative durations. Missing data keeps the metric null. Actionable source delays use live urgent source timestamps and independently annotated onset, never a historical reassessment timestamp or elapsed remote-model processing time. Schema failure rate and visual uncertainty rate describe captured investigation payloads; neither is accuracy or calibrated confidence. Cause accuracy remains null without an independent causal corpus.

`priority_expected` applies to the priority event with the greatest source timestamp across confirmation, live updates and investigations. At equal source timestamps a live event takes precedence over `observed_interval`; conflicting otherwise-equivalent statuses use the more urgent priority. Arrival order and a stored arrival-derived `final_priority` never override the source chronology. `latest_live_priority` excludes historical interval assessments entirely. The report separately includes `interval_priority`, `interval_scene`, and `interval_ts_ms` for the latest investigated source interval. Set `interval_priority_expected` and `scene_expected` to assess that historical interval explicitly. For a reviewed lighter interval, monitoring can correctly pass the interval expectation while the latest live priority still remains urgent; this must not be reported as an actionable-negative live pass. Missing priority timestamps cannot establish a more recent source assessment.

`modelSchemaVerified` requires every captured investigation to contain a received Workers AI output with an empty validation-error array. A `rules_fallback` investigation with `validation_errors: []` does not pass this check. `schema_failure_rate` is measured only over received provider outputs (`source: workers_ai`, no `vlm_error`, and `inference_metadata.mode` fresh or cached when present). Unknown provenance, skipped calls, exceptions and local fallback are excluded, with `schema_eligible_outputs` and `schema_excluded_investigations` exposing the denominator. No eligible provider outputs yields null with `provider_outputs_unavailable`; missing validation fields among eligible outputs also yields null. Legacy explicit Workers AI provenance without inference metadata remains eligible. This measures schema conformance of received outputs, not inference success. `uncertainty_rate` remains the fraction of all captured pipeline investigations classified uncertain, including fallback; it is not a provider-only model uncertainty measure.

Preflight reserves at most two fresh calls per positive/unknown clip and zero per annotated flame-negative clip; batches above `--max-ai-calls` (default: two per clip; technical maximum 256) are rejected before clips start. There is no fixed daily count ceiling; actual calls are admitted by the authenticated batch API using a shared account-day neuron ledger across cameras, including timed-out native calls. There are no automatic inference retries. Runtime state records authoritative fresh/cached/skipped counts and provider token usage, including calls that never produce a cause event. Cause metadata gives per-investigation usage when available. Missing metadata stays unmeasured.

Fresh Scout calls accept a current account-wide Workers AI neuron reading from the Cloudflare dashboard or GraphQL Analytics. Record the source in the snapshot; GraphQL Analytics can lag live requests, so the durable ledger retains new reservations since the start of the UTC day. Each request initially reserves the model's full context cost. A successful response with complete provider token usage settles that reservation to the calculated cost plus a 10% margin; failures and incomplete usage keep the full reservation. Admission is limited to 80% of the reported remaining daily allowance.

For an isolated development comparison of the Scout lighter reassessment, pass `--remote-ai --skip-probe --all-clips --scout-handheld-evaluation --allowance-snapshot CURRENT_USAGE.json` to `scripts/verify_quality_runtime.mjs`. The extra flag requires the complete three-clip batch and a fresh remote allowance snapshot; skipping the separate probe avoids an unnecessary model call. Before creating output or starting Wrangler, the runner validates all three development labels and verifies each attached video's SHA-256 against the annotation. A missing, changed or duplicate input stops before any remote call. The runner enables `SCOUT_HANDHELD_PRIORITY_ENABLED` only in its generated local Wrangler config, and creates a disclosed, expiring `development-fixture` context using `expected_handheld_flame_use` for the single contained-flame clip. Its annotation expects `monitor` for that clip's observed interval while preserving `inspect_urgently` for the live priority. Wrangler debug logs go to the run output directory, while the user's remote authentication configuration remains available. This measures the experimental policy path; it is not a real camera review, a physical-safety finding, or a release gate.

Every replay, including offline and calls without `--require-ai`, must successfully configure that shared development budget before starting a clip. An unavailable API is an error, since absence of a CLI flag does not establish that the target server lacks a remote model binding. Use the verification runner to create the explicit local evaluation profile.

`--inference-cache FILE` opts into a bounded local capture cache; `--cache-mode read_only` replays existing exact-request responses without fresh inference, and `read_write` permits fresh misses within the batch ceiling. `--capture-diagnostics` requests local provider diagnostics. The cache contains provider outputs and optional diagnostics and should remain local. It supplies regression fixtures, never labels or independent quality evidence. Default accelerated replay derives its source clock anchor from video bytes to keep exact requests stable; it does not claim the video's original wall-clock recording time. Use `--realtime` for freshness and lease tests: it anchors at the current epoch and paces source offsets, so timestamped requests may not match an accelerated replay's cache key. Changed images, prompts, model, or inference parameters also miss the runtime cache.

## Free-tier workload profile

Run `node scripts/evaluation/free-tier-profile.mjs --out .hermes/free-tier-profile-YYYYMMDD.json` to exercise one full simulated day through the local Worker and CameraDO handlers: 3 FPS capture, two-second batches, 30-second heartbeats, a long incident, 100 short incidents, 1% identical retries, one durable restart, and a 120-second disconnect recovery. It uses local SQLite surrogates and disables the Workers AI binding.

The report separates exact app request counts from local SQL result/change counts. It estimates indexed writes from the local SQLite schema and counts alarm API calls, but these are still not Cloudflare billing measurements: local query execution does not reproduce rows scanned, service runtime, Workers CPU, account-wide storage or provider neuron use. The `public_free_plan_projection` is a reference to [published Workers and Durable Objects limits](https://developers.cloudflare.com/workers/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/pricing/) and [Workers AI allowance](https://developers.cloudflare.com/workers-ai/platform/pricing/), not proof of this account's plan or remaining promotional credit. `readiness.stages.free_tier_profile` must remain `blocked` until a one-day Cloudflare runtime profile and a timestamped account allowance/usage snapshot supply every required meter with at least 20% headroom.

The readiness input uses `free_tier_profile.meters` entries keyed by `FREE_TIER_METERS` in `readiness.mjs`; each entry has `{ "used": number, "limit": number, "window": "daily|per_invocation_max|current" }`. Daily and per-request limits must come from the effective account plan. Storage values must include account-wide usage, including other databases or Durable Objects. Missing meters block the gate; any measured headroom under 20% or at least 60,000 daily Durable Object row writes fails it.
